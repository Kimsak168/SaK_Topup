VngZz 2 Game API v1.0.0

Accept ABA PayWay KHQR payments: create a payment, show the QR, and confirm it server-side.

Base URL

https://www.vngzz2game.site/api

Authentication

X-API-Key: YOUR_API_KEY

Also accepted: Authorization: Bearer YOUR_API_KEY or ?api_key=YOUR_API_KEY. The legacy https://www.vngzz2game.site/api/payment/request/<key>/v1/... form still works.

POST /v1/generate_qr

Body

FieldTypeRequiredNotes
amountstring|numberyes> 0, max 2 decimals, max 20 chars
currencystringnoUSD (default) or KHR
idempotency_keystringnoAlso accepted as the Idempotency-Key header
payway_link_urlstringnoOverride the hosted PayWay link; falls back if unreachable
metadataobjectnoEchoed back on every response

Request

curl -X POST "https://www.vngzz2game.site/api/v1/generate_qr" \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "content-type: application/json" \
  -d '{"amount":"2.00","currency":"USD","idempotency_key":"order-1001"}'

QR image fields (updated 2026-10-23): the QR image itself is generated by the gateway and passed through the API — use qr_image (a base64 data:image/png URI, render it directly in <img src="…">) or qr_png_url (a hosted PNG link). qr_image_url was the old ABA PayWay CDN link and is now always null since ABA migrated its PayWay host (the old pwapp.ababank.com download URLs no longer exist). check_payload contains only the transaction_id — PayWay credentials never leave the gateway.

POST /v1/check_transaction

Send transaction_id (the API remembers the PayWay credentials), or send client_id, device_id, request_time and token yourself if you store them. GET with the same query parameters is also supported.

curl -X POST "https://www.vngzz2game.site/api/v1/check_transaction" \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "content-type: application/json" \
  -d '{"transaction_id":"TXN-1770000000000-a1b2c3d4"}'

States

stateMeaning
PENDINGQR issued, customer has not paid yet. The background sweeper keeps checking — no need to poll.
PAIDPayWay reported the transaction as approved (action: "approved", payment_status/description APPROVED, payment_status_code: 0, or APV + payer details)
FAILEDDeclined, cancelled or errored
EXPIREDQR TTL elapsed — a late payment may still be picked up by the grace sweep and settled as PAID

Payments are detected automatically even if the customer closes the page: a background sweeper checks every open QR against PayWay every PAYMENT_SWEEP_MS (default 15 s), settles paid transactions to PAID exactly once, and re-checks recently expired rows within PAYMENT_SWEEP_GRACE_SEC for late payments.

Errors & limits

Every error uses the same envelope:

{ "success": false, "status": 400, "code": "INVALID_AMOUNT", "message": "Please enter an amount greater than 0." }
CodeHTTPCause
INVALID_AMOUNT400Amount missing, ≤ 0, too long, or > 2 decimals
INVALID_CURRENCY400Currency is not USD or KHR
MISSING_FIELDS400No transaction_id and incomplete PayWay credentials
INVALID_API_KEY401Wrong key in path or header
TRANSACTION_NOT_FOUND404Unknown transaction_id (or it aged out of memory)
RATE_LIMITED42920 QR/min or 60 checks/min per IP
PAYWAY_ERROR4xx/502Upstream PayWay rejection, raw body included
PAYWAY_TIMEOUT504PayWay did not answer in time
